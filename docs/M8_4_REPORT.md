# M8.4 - Optional human review and collection graph eligibility

**Implementation complete, 21 November 2026.** The M8 workspace now proposes and corrects source-bound claims, presents their exact quotations and entity/relationship mappings, records explicit human decisions, and publishes a current reviewed index. Hybrid + Approved Facts and Graph appear only when that collection has eligible approvals and a matching live projection. Real-paper drafts are pending human review; the agent has not approved them. M8.5 broader cross-topic product verification remains pending.

## User workflow

Open **http://127.0.0.1:8504/** and select **Research papers demo**, then expand **Review claims and connections (optional)**.

1. Choose a source paper, PDF page and passage. Inspect the exact normalized source and its PDF. **Propose claims with local model** requests at most two unapproved drafts from that passage. Exhausted PDF allowances disable extraction; **Enter or correct a proposal manually** remains available without a model call.
2. Choose **Claim to review**. Read the full claim, reporting source, unknown conditions, exact quotes, source spans and entity identities/relationship types. Mechanical validation is only a source/shape check. It does not establish that a statement is supported scientifically.
3. Enter your reviewer name, choose **Approve**, **Reject** or **Needs review**, give your reason, and check the exact-scope acknowledgment. No decision is preselected. Leave review seconds blank if unmeasured. Click **Save my decision**. The timezone-aware submission timestamp is recorded by the app; it is not an estimate of time spent reviewing.
4. Click **Update reviewed index**. Only currently eligible approved claims enter the graph/search index. If publication fails, your decision remains saved, but fact/Graph use stays blocked until the index is current. Vector/Hybrid remain independent.
5. Ask a question using the newly available mode. Graph retains visible requested/effective mode, actual paths and explicit same-profile fallback when no novel graph evidence is selected. No improvement or successful traversal is promised for every collection/question.

To correct a claim, select its source passage, open the manual editor, and choose the existing claim. Save a new **unapproved** revision, review that revision, and update the index. Previous approval never transfers. To revoke an approval, reopen the claim, submit a newer Needs review/Reject decision and update the index. Saved fact/Graph answers are rejected immediately when their approval head changes, even before publication.

The editor defaults to paper-scoped method/dataset identities. Linking two papers through one identity requires an explicit existing-identity selection and its exact name/aliases, followed by human approval. Matching names never automatically merge entities. Evaluation relationships are OF_METHOD/ON_DATASET; findings use ABOUT_METHOD and nonauthoritative dataset MENTIONS. No role promotion or new traversal algorithm was added. A proposal must attribute an evaluation to its own reporting paper; unknown bibliographic type/experimental conditions are not invented.

## Shared boundaries and persistence

- `collections.reviews` owns typed immutable presentations/responses, confined collection/revision review directories, proposal/correction registration, decision receipts and explicit index publication. It reuses `validate_candidate`, `validate_revision`, `import_decisions`, the current-approval projection and `synchronize_review`; no duplicate approval algorithm exists in Streamlit or CLI.
- Every presentation binds the collection marker, journal head, complete claim/source/entity revision, exact support excerpts and validation errors. The saved presentation must match before accepting human input. New `human_ui` provenance records the actual submitted fields and receipt hash; historical CSV/chat serialization remains compatible. This is a local single-user workflow, not authenticated multi-tenant review.
- `collections.proposals` reuses the existing extraction prompt, structured provider factory/schema and quotation validator. A PDF-wide hash-chained journal reserves before inference and retains empty, failed and unknown/interrupted attempts. Successful raw responses survive later registration failure. No automatic retry, provider substitution, source approval or request-cap reset occurs.
- Source SHA-256, not collection name/revision, owns extraction accounting. Public inheritance metadata carries **57 prior reservations across 20 curated PDFs** forward without copying their claims or approval decisions. Total limits remain eight requests/eight selected passages/twelve generated-or-unknown candidates per PDF, at most two candidates/request, 4096 context/1024 output, concurrency one. Manual proposal count is bounded to twelve current claims per paper per collection; corrections preserve history. Paid extraction is explicitly unavailable in this product increment.
- All review mutations, publication and draft extraction use the existing workspace operation lock, serializing them with questions/imports/revision changes. A stale lock/history is an error, never automatically removed. Importing another document creates a new collection revision/review binding; M8 does not silently inherit earlier approvals.
- Fact-mode QA/display/export verifies the current approved projection, live indexes and exact graph materialization through the same services as existing retrieval. Pending, invalid, rejected or revoked claims cannot become evidence. Service/stale/index failures are errors; successful no-new-evidence graph searches alone use the existing explicit fallback.
- `ui.collection_review` owns forms/presentation state only. Read-only reruns/downloads do not generate or encode. Review changes clear saved output. CLI exposes the same review-status/propose/extract/present/decide/publish services, with new output paths required before presentation export. Baseline/reference ranking, six evidence units/1,800 estimated tokens, answer-generation bounds and all prior studies remain unchanged.

## CLI references

Use the M8 checkout and current collection/head. Draft input uses the existing `ProposedClaim` JSON contract; entity mappings are optional explicit kind-to-ID JSON. Human response JSON must come from actual human input against the exported presentation binding; agents must not populate real approvals.

```powershell
& .venv/Scripts/python.exe -m research_assistant.collections review-status --collection <id> --expected-head <collection_sha>
& .venv/Scripts/python.exe -m research_assistant.collections review-extract --collection <id> --expected-head <collection_sha> --chunk-id <chunk_id>
& .venv/Scripts/python.exe -m research_assistant.collections review-propose --collection <id> --expected-head <collection_sha> --chunk-id <chunk_id> --draft draft.json
& .venv/Scripts/python.exe -m research_assistant.collections review-present --collection <id> --expected-head <collection_sha> --claim <claim_id> --output new-presentation.json
& .venv/Scripts/python.exe -m research_assistant.collections review-decide --collection <id> --expected-head <collection_sha> --presentation new-presentation.json --response actual-human-response.json
& .venv/Scripts/python.exe -m research_assistant.collections review-publish --collection <id> --expected-head <collection_sha> --review-head <current_journal_head>
```
